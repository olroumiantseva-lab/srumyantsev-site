# План реализации статического прототипа «Разобрать документ»

Статус: этап 2 выполнен локально; переход к этапу 3 ожидает отдельного подтверждения.

## Результат

Изолированный локальный прототип в `tools/`, состоящий из пяти HTML-страниц, одного общего CSS и одного общего JS. Существующий GitHub Pages-сайт не перестраивается и не изменяется.

## Фаза 1. Каркас и общий визуальный язык

- создать `tools/assets/document.css` с токенами текущего сайта и mobile-first компонентами;
- создать `tools/assets/document.js` только для локальных интеракций;
- использовать общий header/footer, понятную навигацию и статус «Прототип»;
- не подключать внешние шрифты, SDK, аналитику и изображения.

Проверка: CSS не меняет глобальные файлы существующего сайта; страницы работают без сборщика.

## Фаза 2. Пять экранов

- создать landing `/tools/document/`;
- создать login `/tools/login/`;
- создать форму `/tools/document/app/`;
- создать результат `/tools/document/result/`;
- создать историю `/tools/document/history/`;
- связать экраны относительными/корневыми ссылками, соответствующими production URL.

Проверка: обязательные тексты и элементы из спецификации присутствуют, один h1 на страницу.

## Фаза 3. Моковые интеракции

- login: email validation и локальный success-state;
- app: счётчики, limit validation, выборы по умолчанию, переход к результату;
- result: три локальных уточнения и блокировка формы;
- history: confirm dialog, удаление карточек и empty-state.

Проверка: никакие пользовательские данные не отправляются наружу и не сохраняются между сессиями.

## Фаза 4. Browser QA

- запустить локальный HTTP-сервер;
- проверить HTTP 200 для пяти URL;
- пройти happy path и интерактивные состояния в браузере;
- проверить 390×844 и desktop viewport;
- проверить отсутствие горизонтального overflow, единственность h1, доступные labels, min tap targets и отсутствие внешних сетевых интеграций;
- сохранить отчёт проверки в `artifacts/document-prototype-browser-qa.md` без скриншотов с пользовательскими данными.

## Challenge log

### Решает ли план задачу?

Да. Каждому acceptance criterion спецификации соответствует экран или browser-проверка. Backend-функции намеренно представлены только моковыми состояниями.

### Наиболее эффективное решение

1. **Пять автономных HTML с общими CSS/JS** — выбранный вариант. Не требует сборщика, не вмешивается в экспорт Next.js, точно воспроизводит маршруты и легко переносится в отдельное приложение на этапе 3.
2. **Новый React/Vite-проект** — удобнее для будущего backend, но на этапе 2 добавляет зависимости, build pipeline и риск преждевременной архитектуры.
3. **Редактирование существующего Next.js export** — не подходит: исходников приложения в репозитории нет, а правка сгенерированных chunks хрупкая.

### Нет ли кода ради кода?

Исключены component framework, router, state library, дизайн-система, universal product abstraction, persistence и production integrations. JS добавляется только для четырёх проверяемых моковых взаимодействий.

## Риски и границы

- Моковый CTA оплаты не должен создавать впечатление реальной транзакции.
- Моковый login не должен утверждать, что письмо отправлено.
- Прототип проверяет понятность интерфейса, но не доказывает безопасность будущего backend.
- Переход к этапу 3 запрещён без отдельного подтверждения пользователя.
