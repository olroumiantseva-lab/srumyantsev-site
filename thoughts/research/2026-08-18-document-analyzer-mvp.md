# Исследование MVP «Разобрать документ»

Дата: 2026-08-18
Статус: этап 1, исследование до кода

## Цель исследования

Проверить текущую архитектуру `srumyantsev.ru` и выбрать минимально инвазивный способ добавить один платный интерактивный продукт «Разобрать документ», не превращая решение в платформу мини-продуктов и не перенося существующий сайт без необходимости.

## Ограничение GitHub Pages

GitHub Pages является статическим хостингом и не поддерживает серверный код. Кроме того, правила GitHub Pages прямо говорят, что сервис не предназначен для интернет-магазинов, коммерческих транзакций и SaaS. Поэтому размещать платный продукт целиком на GitHub Pages нельзя считать устойчивой production-архитектурой.

Следствие: текущий публичный сайт можно оставить на GitHub Pages, но запросы `/tools/*` следует обслуживать отдельным приложением через маршрутизацию на уровне домена/CDN. До согласования такой инфраструктурной схемы допустим только локальный статический прототип.

## Рассмотренные варианты

### 1. Статический `/tools/` на GitHub Pages + API на отдельном домене

Плюсы: минимальные изменения репозитория и DNS.
Минусы: платный SaaS-интерфейс остаётся на GitHub Pages и конфликтует с ограничениями сервиса; CORS и auth сложнее; решение не рекомендуется.

### 2. `tools.srumyantsev.ru` как отдельное приложение

Плюсы: самый простой деплой, не затрагивает текущий apex-сайт.
Минусы: не выполняет заданные URL `/tools/document/...`; пользователь и auth переходят на другой origin. Возможен только после явного изменения требования к URL.

### 3. Маршрутизация `/tools/*` через Cloudflare перед доменом

Плюсы: сохраняются заданные URL и текущий GitHub Pages как origin для всего остального сайта; новый продукт изолирован; backend и секреты находятся вне GitHub Pages.
Минусы: нужно подключить домен к Cloudflare и настроить route/origin; это изменение доменной инфраструктуры и отдельный сторонний сервис, поэтому требуется согласование.

### 4. Перенос всего сайта на Vercel/Cloudflare Pages/другой full-stack hosting

Плюсы: единый origin и простой роутинг.
Минусы: противоречит требованию не переносить существующий сайт без необходимости; увеличивает риск регрессий. Не рекомендуется для MVP.

## Рекомендованная архитектура

Рекомендация: вариант 3, узкий path-based split без платформенного слоя.

### Публичная часть

- Существующий сайт остаётся в текущем репозитории и продолжает собираться/публиковаться как сейчас.
- Cloudflare становится входной точкой домена.
- Все обычные пути проксируются в существующий GitHub Pages origin без изменения контента.
- Только `/tools/*` направляется в отдельное приложение MVP.

### Приложение MVP

- Один небольшой TypeScript frontend для конкретного продукта, без каталога продуктов и универсального product engine.
- Страницы: landing, login/auth callback, app, result/session, history, buy/success, privacy, terms и user-content rules.
- Дизайн-токены копируются из текущего сайта, но компоненты создаются специально под бытовой сервис.

### Backend, auth и база

- Supabase: Postgres, passwordless email magic link, Row Level Security и Edge Functions.
- Все таблицы с пользовательскими данными закрыты RLS по `auth.uid() = user_id`.
- Клиент не пишет напрямую в журнал кредитов и покупки. Анализ, списание кредита, webhook и удаление выполняются серверными функциями/транзакциями.
- `credit_transactions` остаётся источником истины; баланс вычисляется SQL-функцией или транзакционным запросом. Кешированный баланс добавлять только при подтверждённой необходимости.
- Первоначальный анализ реализуется атомарно: резерв/проверка кредита, вызов OpenAI, сохранение успешного результата и `-1` в одной защищённой серверной операции. При timeout/error кредит не списывается. Нужно отдельно защититься от двух параллельных запросов одного пользователя.
- Webhook использует уникальное ограничение `(provider, provider_payment_id)` и транзакцию `purchase + credit_transaction`, поэтому повтор события не начисляет кредиты.
- Удаление по требованиям MVP — физическое удаление содержимого исходного текста, результата и follow-up. Метаданные аудита, если необходимы для платежей/аналитики, должны храниться отдельно и без текста документа.

### OpenAI

- Серверный Responses API со Structured Outputs (`json_schema`, strict mode), а не свободный JSON-текст.
- Стартовая модель-кандидат: `gpt-5-mini`, вынесенная в конфигурацию. Финальный выбор закрепить после тестового набора русскоязычных документов и сравнения качества/цены; интерфейс от модели не зависит.
- Исходный документ передаётся только с backend; API key хранится в secrets Edge Functions.
- Не включать web search, file search и другие инструменты: MVP должен отвечать только по предоставленному тексту.
- В application logs сохранять request/session ID, длительность, статус, коды ошибок и usage, но не документ, контекст пользователя и полный ответ.

### Аналитика

- Использовать уже установленную Яндекс.Метрику и явные цели/события из ТЗ, без нового рекламного SDK.
- События, связанные с деньгами и кредитами (`purchase_success`, `repurchase_success`, `analysis_success`), дополнительно фиксировать сервером, потому что клиентские события могут блокироваться или дублироваться.
- Webvisor на страницах, где пользователь вставляет документы, несёт риск захвата чувствительного текста. Для `/tools/*` запись форм и содержимого должна быть отключена или эти страницы должны использовать отдельную конфигурацию аналитики без записи полей.

## Что не строим

- универсальную платформу мини-продуктов;
- каталог продуктов, тарифный движок и подписки;
- универсальные payment/auth/OpenAI abstraction frameworks;
- загрузку файлов, OCR, PDF/DOCX и админскую CRM;
- миграцию всего сайта на новый стек.

Абстракция платёжного провайдера ограничивается маленьким интерфейсом `createCheckout` / `verifyWebhook` и нормализованным событием оплаты. Остальная бизнес-логика остаётся продуктовой.

## Нерешённые решения и гейты

1. Платёжный провайдер не указан. Его нельзя выдумать: нужны название провайдера, доступы/тестовый режим, требования к чекам и webhook.
2. Подключение Cloudflare и Supabase — сторонние сервисы и изменение инфраструктуры домена; перед production-настройкой требуется отдельное согласование.
3. Supabase Free подходит для прототипа, но free-проекты могут приостанавливаться после недели неактивности; production требует согласованного тарифа/риска.
4. Нужно определить отправителя magic-link писем и почтовый домен. Стандартный SMTP/branding Supabase не следует считать готовым production-решением без проверки доставляемости.
5. Юридические тексты нельзя генерировать как финальные документы без реквизитов, перечня обработчиков, сроков хранения и выбранных провайдеров. Сначала возможны только черновики на согласование.

## Проверяемые критерии для следующего этапа

- Статический прототип воспроизводит пять экранов из ТЗ на мобильном и desktop.
- Прототип не вызывает OpenAI, оплату, auth и production analytics.
- Существующие страницы сайта и их файлы не меняются, кроме согласованных ссылок после готовности продукта.
- До backend-реализации зафиксированы схема БД, RLS, транзакции кредита, idempotency webhook, rate limits и политика логирования.
- До production deploy пройден E2E в тестовом окружении и получено отдельное разрешение на публикацию.

## Итог

Лучший вариант для заданных URL и минимального риска — оставить существующий контент на GitHub Pages как origin, поставить перед доменом Cloudflare и направить только `/tools/*` в отдельное приложение на Supabase-backed serverless-стеке. Это сохраняет основной сайт, изолирует секреты и платёжный продукт и не создаёт платформу. Реализацию следует продолжать по фазам только после согласования этой схемы; ближайший безопасный шаг — статический локальный прототип без внешних интеграций.
