# Спецификация этапа 3: Supabase Auth, база и серверный mock

## Цель

Превратить прототип в приложение с реальными пользователями, magic-link входом, сохранением разборов, ledger кредитов и серверным mock-анализом. OpenAI, оплата и production-маршрутизация Cloudflare не входят в этап.

## Пользовательский сценарий

1. Анонимный пользователь видит лендинг, но `/app`, `/result` и `/history` требуют сессию.
2. На `/tools/login/` пользователь запрашивает одноразовую ссылку по email.
3. После перехода по действующей ссылке Supabase восстанавливает сессию и открывает `/tools/document/app/`.
4. Приложение показывает баланс из `credit_transactions`.
5. Пользователь отправляет документ в защищённую Edge Function.
6. Функция проверяет JWT и входные данные, создаёт deterministic mock-result и атомарно сохраняет разбор вместе с `-1` кредитом.
7. Если mock/серверная операция завершается ошибкой, ни сессия, ни списание не появляются.
8. Три уточнения сохраняются как пары user/assistant и не меняют баланс. Четвёртое отклоняется сервером.
9. История и результат читаются только владельцем через RLS.
10. Удаление очищает пользовательское содержимое, удаляет follow-up и оставляет tombstone без текста.
11. Logout удаляет клиентскую сессию. Повторный magic-link вход показывает сохранённую историю.

## Данные

- `auth.users` — источник идентичности Supabase;
- `profiles` — профиль приложения, 1:1 с `auth.users`;
- `purchases` — подготовленная, но не используемая структура будущих оплат;
- `credit_transactions` — неизменяемый ledger;
- `document_sessions` — документ, контекст, выбранные цели и результат;
- `followup_messages` — сообщения уточнений.

## Безопасность

- RLS включён на всех таблицах `public` с пользовательскими данными.
- Пользователь имеет прямой `select` только собственных активных sessions/messages, своего profile и ledger.
- Прямые insert/update/delete для business-таблиц запрещены; мутации выполняют Edge Functions через service-only SQL functions.
- Edge Functions сначала проверяют Supabase JWT и получают user ID из проверенной сессии, не из тела запроса.
- Service role используется только внутри Edge Functions.
- Документы, контекст, результаты и follow-up не выводятся в логи.
- История не содержит preview исходного текста или ответа.

## Кредиты

- Баланс равен сумме ledger.
- Создание разбора сериализуется advisory lock по user ID и проверяет баланс внутри той же транзакции.
- Списание и document session создаются одной SQL-функцией; частичный результат невозможен.
- Dev-начисление доступно только Edge Function без UI, только в non-production окружении и только email из allowlist.
- Повторный `reference_id` не начисляет кредиты дважды.

## Ошибки

- 401: вход требуется или ссылка устарела;
- 402/409 application code: нет кредитов;
- 400: пустой/слишком длинный документ, контекст или вопрос;
- 403/404: чужой или удалённый разбор не раскрывается;
- 500/timeout: понятное сообщение, кредит не списан.

## Критерии приёмки

1. SQL migrations создают все таблицы, индексы, constraints, triggers, RLS policies и service-only RPC.
2. Magic link использует `signInWithOtp`, разрешённый redirect и сохраняемую browser session.
3. Неавторизованные app/result/history перенаправляются на login.
4. Создание разбора, follow-up и удаление идут через JWT-protected Edge Functions.
5. История и повторный вход работают на постоянных данных Supabase.
6. Ledger списывает ровно один кредит только при успешной записи.
7. Межпользовательская изоляция доказана тестом A/B.
8. Service-role key отсутствует во frontend и git.
9. Логи функций не содержат пользовательского текста.
10. Полный remote/local Supabase E2E пройден до признания этапа завершённым.

## Внешний блок

Для фактического E2E необходим либо Docker + Supabase CLI, либо hosted Supabase project с project URL, publishable key и правом применить migrations/functions. Без одного из этих вариантов код можно подготовить и статически проверить, но нельзя заявить о работающем magic link или RLS в реальной БД.
